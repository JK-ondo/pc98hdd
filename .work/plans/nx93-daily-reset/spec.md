# 仕様: RANK.EXE 毎日更新（nx93-daily-reset）

対象: `nx93rank/dist/RANK.C`（現行 1302 行）と `nx93rank/dist/GAME.BAT`。
出発点は `plan.md` の決定事項・設計上の帰結・跨ぎの規則・更新の順序。本仕様はそれらを
覆さず、観測可能な契約に落とす。体裁の前例は
`.work/plans/nx93-ranking-reset/test-design.md`。

§3.5 のアンカー表 15 行は、曜日を含めて独立に検算済み（2026-10-20）。

## 1. 目的

週次リセットだけでは毎日遊ぶ人にとって席が空くのが遅い。`RANK.EXE` に毎日更新を追加し、
週次／毎日をコマンドライン引数（`GAME.BAT` の 1 行）で切り替えられるようにする。
同時に、毎日化で年 3650 行増える JSON 台帳をやめ、消した記録の行き先を
「歴代トップ 30（`RANK30.TXT`）」と「ユーザごとの最高記録（`RANKWHO.TXT`）」の
固定サイズ・平文 2 枚へ集約する。98 上で `TYPE RANK30.TXT` とすればそのまま読めること
（記録を人が見られること）が JSON より優先される。

判定は「経過日数」から「暦の境界を跨いだか」へ変わる。日曜 23:59 に遊んで月曜 00:01 に
遊べば、週次でもリセットが起きるようになる。

あわせて `rank_rebuild` の埋め行重複を直す（§3.6、2026-10-20 ユーザー決定）。

## 2. 非目標

- モードの永続化はしない。`NX93.TXT` に `mode` 欄は作らない（引数が唯一の出所）。
- `RANK30.TXT` / `RANKWHO.TXT` からの復元・編集・剪定機能は作らない（併合規則が許す
  変化のみ）。旧台帳からの個別レストア機能も作らない。
- `NX93.EXE` 側の読み取り互換は「`NX93.SCR` を 10 行・バイト保存で書く」以上に保証しない。
- `NX93.BAK` には読みも書きも触れない（ゲーム本体の持ち物）。
- タイムゾーン・夏時間・うるう秒の扱いは現行のまま（civil-day 算術、秒クランプ）。
- 終了コードの語彙は {0, 1} のまま増やさない。`GAME.BAT` の `errorlevel 1` 分岐は不変。
- リセット後の `NX93.SCR` の組み立ての骨格（各人の最高 1 件＋出荷時 10 行からスコア降順で
  上位 10）は変えない。変えるのは §3.6 の埋め行除外 1 点のみ。

## 3. 公開面

### 3.1 起動と引数

```
RANK            週次（無指定の既定。現行 GAME.BAT との後方互換）
RANK /W         週次
RANK /D         毎日
RANK /w  /d     小文字も同義（DOS のスイッチ慣習。strcmp 4 本で判定し <ctype.h> は使わない）
```

- 引数が 2 個以上、または上記 4 綴り以外（`/X`、`FOO`、`-D`、`/DD`、空文字列 等）
  → **何も開かず・何も書かず**、usage（`/D` と `/W` を字面で含む）を表示して終了コード 1。
  黙って既定へ落とすと打ち間違いが毎日リセットに化けるため。
- 事後条件: 終了コードは 0（無処理またはリセット成功。警告 W1 を含む）か
  1（拒否・失敗。何が書き換わったかは §5 の表のとおり）のみ。

`GAME.BAT` の契約:

- `RANK` の呼び出し行がスイッチを 1 個持つ。**出荷時は `/D`**（2026-10-20 ユーザー決定。
  本機能の動機が毎日更新であり、送った時点でそれが有効になる）。
- 更新頻度の変更＝この 1 行の編集、という運用をコメントで説明する。
- `if errorlevel 1` → 日本語メッセージ＋ `PAUSE` → `NX93` 起動、は現行のまま。

### 3.2 画面出力（メッセージの事実要件）

文字列の字面は実装の裁量とし、次の事実を含むことだけを契約とする。すべて ASCII、
接頭辞 `RANK:`、ランキング行のバイト列は `fputs`/`fputc` 系でのみ出す
（printf 系の書式引数には渡さない。`Bio_100%` が居る）。

| 状況 | 必ず含む事実 |
| --- | --- |
| 終了 0（無処理） | 有効なモードの字句 `weekly` または `daily`、何もしなかったこと、および**最終リセットからの経過日数**（現行の「last reset was N day(s) ago」を保つ。`rank_elapsed_days` と `rank_put_days` はこのために生き続ける。跨ぎ判定には使わない） |
| 終了 0（リセット） | モードの字句、リセットしたこと。移行を行ったときは加えて旧台帳を `NX93OLD.TXT` へ退避したこと |
| 警告 W1（ユーザ上限超過） | `RANKWHO.TXT` が満杯であること、落とした行の raw バイト列そのもの（1 件につき 1 報） |
| 警告 W2（退避の片付け） | 片付ける退避名（`RANKOLD.30` / `RANKOLD.WHO` / `RANKOLD.SCR` / `RANKOLD.TXT` のいずれか）、それが消えること、必要なら次回起動前に退避すべきこと（1 件につき 1 報） |
| 終了 1（各エラー） | 条件の名指し、**実際に差し替わったファイルと差し替わらなかったファイルの区別**、できる対処（`DATE`、`ATTRIB -R`、退避名からの rename、再実行で続きから直ること 等） |

W1 の報告は併合の計算時点（コミット前）に出てよい。ただしその後に失敗した場合、
失敗メッセージが「どのファイルが実際に替わったか」を正しく述べることで訂正する。
W1 は終了コードを変えない（2026-10-20 ユーザー決定。終了コードの語彙を {0,1} に保つ）。

画面 1 行は NX93 の起動で流れうる。落ちた行が後から読めるのは、**同じ行が既に
`RANK30.TXT` に入っているときだけ**である。`RANKWHO.TXT` の既存行が落ちる場合、その行は
どこからも歴代表の入力にならない（§3.6 の候補は各表自身の既存行と `NX93.SCR` の行だけで、
ユーザ別表の行は歴代表へ流れない）ので、歴代 30 に無ければ画面の 1 行が唯一の記録になる。

### 3.4 ファイル形式

**`NX93.SCR`** — 変更なし。読みは CR LF / LF / CR / 末尾 0x1A 許容・空行スキップ・
10 行上限・長さ 27..35 の形状検査。書きはちょうど 10 行・各行 raw + CR LF・末尾 0x1A なし。

**`RANK30.TXT` / `RANKWHO.TXT`（新設・平文）** — `NX93.SCR` と同じ行形式・同じ読み書き規約:

- 行は `rank_parse_line` が受理するバイト列そのもの（スコア 1..9 桁＋固定 26 バイト）。
  プログラムが行を合成・加工することはない（I8）。
- 書き: 0 行以上・各行 raw + CR LF・最終行も CR LF 終端・末尾 0x1A なし・空行なし。
  並びはスコア降順、同点は表へ入った順（先入れが上）。
- 読み: `NX93.SCR` と同じ寛容さ（CR/LF/CRLF、末尾 0x1A、空行スキップ）。並びは検証しない
  （読み込み時に安定整列で正規化する）。1 行でも受理できない・行数超過（30 / 100）・
  行バッファ超過は全体を拒否（fail closed、E7/E8）。
- `RANK30.TXT` は最大 30 行。同一行（全バイト一致）は 1 件。
- `RANKWHO.TXT` は最大 100 行、**1 key（§3.8 の同一判定規則）につき 1 行**。
  読み込んだファイルに key 重複があれば破損として拒否する（E8）。
- ファイル不在はエラーではなく 0 行の表（新規導入が自己修復する。現行 D6 と同型）。

**`NX93.TXT`（新形式・状態のみ）** — 正準形は次の **45 バイト固定**。
旧 writer と同じ接頭辞なので、既存の `rank_ledger_read_last_update` がそのまま読める。

```
{<CR><LF>
  "lastUpdate": "YYYY-MM-DDTHH:MM:SS"<CR><LF>
}<CR><LF>
```

- オフセット 20..38（0 起点、19 バイト）がタイムスタンプ。それ以外の 26 バイトはリテラル。
- 正準判定（`rank_state_check`）は「全長 45、リテラル部が全バイト一致、
  20..38 が `rank_time_parse` を通る」の完全一致。余分な末尾バイトも不一致。
  この厳格さは意図的: 壊れた旧台帳を「新形式だ」と誤認して捨てる経路を塞ぐ（E10）。
  将来フィールドを足すときはこの検査ごと更新する（前方互換より fail closed を取る）。
- `lastUpdate` は最終**リセット**時刻。リセットしない起動では書き換えない。

**旧 `NX93.TXT`（旧台帳。読み取り専用・移行の入力）** — 受理する文法は旧 writer
（現行 `rank_ledger_write`）の出力＋トークン間空白の揺れのみ。これ以外は移行失敗（E12）。

```
ledger  := prefix '"backups"' ws ':' ws '[' ws entries? ws ']' ws '}' ws 0x1A? EOF
entries := entry (ws ',' ws entry)*
entry   := '{' ws '"backupAt"' ws ':' ws string ws ',' ws '"ranking"' ws ':'
           ws '[' ws strings? ws ']' ws '}'
strings := string (ws ',' ws string)*
string  := '"' char* '"'
char    := 0x20-0x21, 0x23-0x5B, 0x5D-0xFF の生バイト
         | '\"' | '\\' | '\u00' hex hex   （hex は大小とも可。00XX 以外の \uXXXX は不受理）
ws      := (SP | TAB | CR | LF)*
```

- `prefix` は先頭から最初の 9 バイト列 `"backups"` まで（引用符を含めて 9 バイト。
  `lastUpdate` は従来どおり
  別スキャンで先に取り出す）。名前欄 8 バイトに引用符込みの `"backups"` は収まらないため
  誤マッチしない（現行コードの同種の論証と同じ）。
- 文字列中の生の 0x00–0x1F は不受理（旧 writer は必ず `\u00XX` に逃がしている。
  Mac で UTF-8+LF 化された写しも文字列内は無傷）。
- `ranking` の各文字列はデコード後 63 バイト以下で、`rank_parse_line` を通ること。
  どちらかが破れたら移行全体を失敗させる（行を黙って捨てない。現行 D4 の対称）。
- `backupAt` の値は文法どおりの string ならば内容は検査しない（使わない値を縛らない）。

### 3.5 跨ぎの規則（判定仕様）

基点は `NX93.TXT` の `lastUpdate`（最終リセット時刻）、相手は現在時刻。
**経過時間ではなく暦の境界**で判定する。`rank_elapsed_days >= 7` の現行規則は廃止。

1. **未来検出が先。** 年月日時分秒の全体の辞書式比較で `now < lastUpdate` なら
   終了 1・無変更（E5）。同日中に数時間巻き戻った RTC 異常もここで捕まる。
2. **毎日（`/D`）**: `rank_days_from_civil(lastUpdate の年月日) != 同(now)` ならリセット。
   深夜 0 時ちょうど（00:00:00）は新しい日に属する。
3. **週次（`/W`・無指定）**: 月曜起点の週番号
   `w(days) = floor_div(days + 3, 7)` が異なればリセット。
   1970-01-01 は木曜なので +3 で月曜境界に揃う。月曜 00:00:00 は新しい週に属する。
4. 境界を何本跨いでいてもリセットは 1 回（I10）。
5. `NX93.TXT` 不在は初回とみなし、その起動でリセットする（現行決定の踏襲）。

### 3.6 リセットの手順と併合規則

リセットが確定した起動は、読みをすべて終えハンドルを閉じてから
（`NX93.TXT` は rename されるので特に）、**この順**で 1 ファイルずつ
「一時へ全書き → 3 段 commit（退避 → 差し替え → 退避削除）」する:

1. `RANK30.TXT` 2. `RANKWHO.TXT` 3. `NX93.SCR` 4. `NX93.TXT`

`NX93.SCR` は唯一「失うもの」なので、その記録が 1・2 に載った後でなければ消えない。
4 を最後に置くので、途中で落ちても次回起動が同じリセットをやり直す（I1/I4）。

**候補**: リセット前 `NX93.SCR` の全行のうち、出荷時 10 行（`rank_default_line(0..9)`）
のいずれかと**全バイト一致しない**行。`Bio_100%` の埋め行は記録ではないので
歴代表・ユーザ別表に入れない。一致判定はバイト一致のみ（名前が Bio_100% でも
日付やスコアが違えば実在の記録として扱う）。

**併合の適用順**（同点時の順序を一意にする）: (1) 読み込んだ既存表の行（ファイル順）、
(2) `NX93.SCR` の候補行（ファイル順）、(3) 移行時のみ旧台帳の行（§3.7）。

**`RANK30.TXT` への 1 行併合（`rank_merge30`）**:

- 候補が既定行 → 変化なし。表に全バイト一致の行が既にある → 変化なし（重複除去）。
- それ以外: スコア降順を保つ位置（同点行の**後ろ**）へ挿入。31 行になったら最終行
  （最下位。同点なら最後に入った側）を黙って落とす — 歴代 30 の床を割るのは仕様。
- 事後条件: 行数 ≤ 30、スコア降順、同点は挿入順。同じ候補列を二度流しても不変（冪等）。

**`RANKWHO.TXT` への 1 行併合（`rank_mergewho`）**:

- 候補が既定行 → 変化なし。
- 同じ key の行が既にある: 候補スコアが**真に大きい**ときだけ行ごと差し替え
  （降順位置へ入れ直す）。同点以下は既存を保持。差し替えで消える旧行は本人の更新であり
  **報告しない**。
- key が無い: 挿入。101 人目になったら**最下位の 1 行**（降順・安定なので表の最終行。
  挿入した候補自身でありうる）を落とし、落とした行を **W1 として報告する**（黙って消さない）。
- 事後条件: 行数 ≤ 100、key は互いに異なる、スコア降順・同点は挿入順。冪等。

**`NX93.SCR` の再構築（`rank_rebuild`、2026-10-20 に 1 点変更）**:

- 骨格は現行どおり「各人の最高 1 件 ＋ 出荷時 10 行からスコア降順で上位 10」。
- **変更点: 入力 `cur` の行のうち出荷時 10 行と全バイト一致するものを、重複除去の前に
  除く。** 現行は埋め行を「Bio_100% という選手の記録」として重複除去に参加させたうえで
  出荷時 10 行を無条件に足すため、埋め行を含む表を再構築すると 200000 の `Bio_100%` が
  2 行並び、下位の 060000/040000/020000 が押し出されていた。実機の現 `NX93.SCR` は
  埋め 4 行を含むので、これは次回リセットで実際に出る。
- この変更の副産物として `rank_rebuild` は**冪等**になる（I12）。リセット済みの表を
  再度リセットしてもバイト同一。中断からの収束（I4）の表明がこれで強くなる。
- **I12 の帰結: `NX93.SCR` を変化させる入力は限られる（2026-11-10 追記）。** 鍵ごとの
  最高 1 件＋出荷時 10 行から降順上位 10 を取るので、**記録がすべて別人の表は、それ自身が
  不動点**である。したがって `NX93.SCR` が変わるのは、鍵が畳まれて行が減るか、候補が
  出荷時の埋め行を押し出すかのどちらかに限られる。高スコアの行を 1 本足しただけの表は
  変わらない。試験でリセット前後の差を観測したい場面でここを踏み抜きやすい。
- **既存テスト U-M1〜U-M10 の期待値は、この規則だけでは 1 つも変わらない**（確認済み:
  U-M* のどの入力も出荷時 10 行とバイト一致する行を `cur` に持たない）。実装中に U-M* が
  この規則のせいで赤くなったら、それは期待値の更新ではなく回帰である。新規則の網は
  新設ケースが張る。期待値が変わるのは §3.8 の鍵規則のほうで、そちらは
  `OMZN@@@@` / `OMZN++++` を含む入力の期待値を実際に動かす。

**`NX93.TXT`**: 正準 45 バイトを `now` で書く。

### 3.7 移行（旧台帳の取り込み）

- **発火条件**: リセットが確定した起動で、`NX93.TXT` が正準 45 バイト形でなく、
  かつバイト列 `"backups"` を含む。リセットしない起動では検査も移行もしない
  （「リセットしない起動では何も書かない」の帰結。旧台帳は最初の跨ぎまでそのまま残り、
  `lastUpdate` の読み出しにだけ使われる）。
- **前提検査**: `NX93OLD.TXT` が既に存在すれば何も書かずに終了 1（E11）。
  過去の退避を黙って上書きして失わないため。再取り込みをやり直したいときは
  ユーザが `NX93OLD.TXT` を手で移してから実行する（併合が冪等なので再取り込み自体は無害）。
- **取り込み対象と順序**: `backups[].ranking[]` の**全行**。ファイルの並びのまま
  （先頭＝新しいバックアップから、各 `ranking` 内は上から）。§3.6 の適用順 (3) として
  `NX93.SCR` 候補の後に流す。既定行一致は入れない。デコード（§3.4 の文法）→
  `rank_parse_line` → `rank_merge30` / `rank_mergewho`。表はメモリ内で組み上がるので、
  **文法違反・読めない行が 1 つでもあればディスクに 1 バイトも書かずに終了 1**（E12）。
  旧台帳は 1 行ずつストリームで読み、全体をメモリに載せない（2 MiB 台帳でも動く）。
- **書き出し**: §3.6 の順序 1〜3 は通常どおり。4 だけ退避先が変わる:
  `NX93.TXT` → `NX93OLD.TXT` へ rename（keep）、`RANKTMP.TXT`（正準 45 バイト）→
  `NX93.TXT` へ rename。**成功しても `NX93OLD.TXT` は削除しない**。
  2 段目が失敗したら `NX93OLD.TXT` → `NX93.TXT` へ戻す（通常 commit と同じ復帰規則）。
- **二度目は走らない保証**: (a) 成功後の `NX93.TXT` は正準形で `"backups"` を含まないため
  発火条件が構造的に成立しない。(b) 旧台帳を故意に書き戻しても、E11 が先に止めるか、
  `NX93OLD.TXT` を除けたうえでの再取り込みは冪等で結果を変えない。
  観測: 移行成功後の任意の回数の起動で `NX93OLD.TXT` がバイト不変。
- **途中失敗時の状態**は §5 の E13〜E16 の表に従う（取り込みはメモリ内なので、
  commit が始まる前の失敗はすべて「無変更」）。

### 3.8 プレイヤの同一判定（2026-10-21 ユーザー決定）

名前欄に `omzn@@@@` `omzn++++` のように末尾へマークを付ける人がいる。マークは同じ人の
印であって別人の印ではないので、識別に使わない。鍵（`RankRow.key`）の作り方を次に変える。

変更前（現行 `rank_fold_key`）: 前後の 0x20 を落とし、ASCII `a-z` を大文字へ畳む。
変更後: そこに「末尾のマーク落とし」を 1 段挟む。

1. 名前欄 8 バイトの前後から 0x20 を落とす。これを `trimmed` と呼ぶ。
2. `trimmed` の**末尾から**、「ASCII（< 0x80）かつ `A-Z a-z 0-9` でない」バイトを
   落ち続けるかぎり落とす。**0x80 以上のバイトに当たったら止める。**
   これは必須条件であって最適化ではない: Shift-JIS の名前は 0x80 以上のバイトで終わるので、
   「英数字でない」を素朴に適用すると日本語名が丸ごと消えて鍵が空になり、
   別人どうしが全員同一人物に潰れる。
3. 2 の結果が空になったら `trimmed` をそのまま使う（`@@@@` だけの名前が、
   同じく空になる他のマークだけの名前と同一人物に潰れるのを防ぐ）。
4. 結果の ASCII `a-z` を大文字へ畳む。0x80 以上のバイトは素通し（現行どおり。
   `<ctype.h>` は使わず、`unsigned char` で手ずから比較する）。

| 名前欄 | 鍵 | 備考 |
| --- | --- | --- |
| `omzn    ` | `OMZN` | |
| `OMZN    ` | `OMZN` | 大文字小文字は無視（現行どおり） |
| `OMZN@@@@` | `OMZN` | **変更点。現行は `OMZN@@@@` で別人だった** |
| `omzn++++` | `OMZN` | 同一人 |
| `omzn-2  ` | `OMZN-2` | 内部の記号は残る（末尾が英数字なので何も落ちない） |
| `omzn-   ` | `OMZN` | `omzn` と同一人。末尾の `-` は落ちる。**すぐ上の `omzn-2` とは結論が分かれる**ので、この隣接対を試験に入れる |
| `omzn` ＋ SJIS 2 バイト | 落ちない | 規則 2 が 0x80 以上で止まる。誤実装と区別できる唯一の形（§7 C.6） |
| `TARO2   ` | `TARO2` | `TARO` とは別人 |
| `Bio_100%` | `BIO_100` | 末尾の `%` が落ちる。出荷時 10 行は全部同名なので影響なし |
| `@@@@    ` | `@@@@` | 落とすと空になるので規則 3 で元のまま |
| `        ` | （空） | 現行どおり。空白だけの名前どうしは同一人物 |
| Shift-JIS 名 | 末尾まで保存 | 規則 2 が 0x80 以上で止まる |

この鍵は `rank_rebuild` の重複除去と `RANKWHO.TXT` の 1 人 1 行の両方に使われるので、
両方が同時に併合側へ動く。歴代 30（`RANK30.TXT`）は行バイト列で重複除去するので無関係。

実機への帰結: `OMZN`（327400）と `OMZN@@@@`（299370）が同一人物になり、現 `NX93.SCR`
（実記録 6 行＋埋め 4 行）をリセットすると、実記録として残るのは 327400 の 1 行だけ、
残る 9 行は出荷時の 200000..040000 になる。消えた 5 行は `RANK30.TXT` に全部入る。

`RANKWHO.TXT` は本変更で新設するファイルで、まだどこにも存在しない。したがって
「旧規則で書かれた `RANKWHO.TXT` が新規則では key 重複になる」という移行問題は生じない
（もし手で作って持ち込めば E8 で止まる。それが正しい振る舞い）。

### 3.9 C の契約

#### 定数・型（新設／変更）

```c
#define RANK30_ROWS   30                /* new: all-time table rows */
#define RANKWHO_ROWS 100                /* new: per-user table rows */
#define RANK_MODE_WEEKLY 0              /* new */
#define RANK_MODE_DAILY  1              /* new */
/* RANK_PERIOD_DAYS と RANK_WS_MAX は削除（経過日数規則と台帳追記の廃止で死ぬ） */

typedef struct { RankRow row[RANK30_ROWS + 1];  int count; } Rank30Table;  /* new, ~2.7KB */
typedef struct { RankRow row[RANKWHO_ROWS + 1]; int count; } RankWhoTable; /* new, ~8.7KB */
```

`RankTime` `RankRow` `RankTable` は不変。`+1` は「挿入してから落とす」ための作業余白で、
静止状態の count はそれぞれ ≤ 30 / ≤ 100。**これらの表を自動変数に置いてはならない**
（DOS の既定スタックは約 2KB）。

#### 新設関数

```c
/* --- 引数・時刻 --- */
int  rank_mode_parse(const char *arg, int *mode);
     /* NULL -> WEEKLY で 0。"/D""/d" -> DAILY、"/W""/w" -> WEEKLY で 0。
        それ以外 -> -1、*mode 不変。 */
long rank_week_index(long days);
     /* floor_div(days + 3, 7)。月曜起点。アンカーは §3.5 の表。 */
int  rank_time_before(const RankTime *a, const RankTime *b);
     /* 1 iff a < b（6 欄の辞書式、秒粒度）。NULL は 0。 */
int  rank_crossed(const RankTime *last, const RankTime *now, int mode);
     /* 1 = 境界を跨いだ / 0 = 跨いでいない / -1 = NULL または不正 mode。
        毎日: 暦日が異なる。週次: rank_week_index が異なる。
        未来検出は行わない（呼び手が rank_time_before を先に適用する）。 */

/* --- 行と表 --- */
int  rank_is_default_line(const char *raw);
     /* rank_default_line(0..9) と全バイト一致ならその添字、さもなくば -1 */
int  rank_rows_read(FILE *fp, RankRow *rows, int maxrows);   /* 行数 / -1。
        受理規約は rank_read_table と同一（CR/LF/CRLF/0x1A、空行スキップ、
        溢れ・超過・不受理行で -1）。 */
int  rank_rows_write(FILE *fp, const RankRow *rows, int count);  /* 0 / -1。
        各行 raw + CRLF、末尾 0x1A なし、fflush まで。 */
int  rank_r30_load(FILE *fp, Rank30Table *t);
     /* 行数 / -1。<=30 を強制し、スコア降順へ安定整列して格納。 */
int  rank_who_load(FILE *fp, RankWhoTable *t);
     /* 行数 / -1。<=100 と key の相互相異を強制し、安定整列。重複 key は -1。 */
int  rank_merge30(Rank30Table *t, const RankRow *r);         /* 0 / -1(NULL)。§3.6 の規則 */
int  rank_mergewho(RankWhoTable *t, const RankRow *r, RankRow *dropped);
     /* 1 = 1 行落とした（*dropped に複写）/ 0 = 落とさず / -1 = NULL。§3.6 の規則 */

/* --- 状態ファイルと旧台帳 --- */
int  rank_state_write(FILE *fp, const RankTime *now);        /* 0 / -1。正準 45 バイト */
int  rank_state_check(FILE *fp);                             /* 1 = 正準 / 0 = それ以外 */
int  rank_has_backups(FILE *fp);                             /* 1 / 0。"backups" 走査 */
int  rank_ledger_string(FILE *fp, char *buf, int bufsize);
     /* 開き引用符の直後から 1 文字列をデコード。長さ / -1（不正エスケープ・溢れ・EOF） */
int  rank_import_ledger(FILE *fp, Rank30Table *t30, RankWhoTable *who);
     /* 0 / -1。先頭から §3.4 の文法で backups 全行を取り込み、W1 をその場で報告する。
        -1 のとき t30/who は信用しない（呼び手はリセットを中止する）。 */
```

#### 契約が変わる既存関数

```c
int rank_run(const char *dir, int mode);
    /* 引数 mode が増える。mode が WEEKLY/DAILY 以外 -> 何も書かず 1。
       0 = 無処理またはリセット成功、1 = 失敗（§5 の表どおりの残留状態）。
       dir の意味（NULL/"" は裸のファイル名、非空は結合）は不変。 */

    /* argc<=1 -> 無指定、argc==2 -> rank_mode_parse、argc>2 または parse 失敗 ->

       重複除去が使う鍵は §3.8 で変わるので、OMZN と OMZN@@@@ が同一人物として

    /* 受理規則・raw・score・name は不変。out->key の中身だけが §3.8 で変わる。

```

`rank_put_days` `rank_say`、および内部の 3 段 commit 規則
（FAILED は dst 無傷、STRANDED は dst 消失＋keep に旧バイト。移行の 4 枚目だけ
keep が `NX93OLD.TXT` で、成功時に削除しない点が追加）。

#### 削除する既存関数・記号

`rank_ledger_write`（台帳追記の廃止）、`rank_json_escape`（書く JSON 文字列が
なくなる）、`RANK_PERIOD_DAYS`、`RANK_WS_MAX`。死んだコードは残さない。

#### テスト継ぎ手（DOS ビルドには入らない: 既存 S5 検査が引き続き拘束）

`RANK_NO_MAIN` / `RANK_TEST_CLOCK`（`rank_test_now`）は現行のまま。
`RANK_TEST_FAULT` の注入点は 4 ファイル×3 種＋移行の退避 rename に拡張する
（旧 `RANK_FAULT_LEDGER_*` は `RANK_FAULT_TXT_*` に改名。テスト専用面なので互換不要）:

```c
typedef enum {
    RANK_FAULT_NONE = 0,
    RANK_FAULT_R30_WRITE, RANK_FAULT_R30_COMMIT,
    RANK_FAULT_R30_RENAME, RANK_FAULT_R30_STRAND,
    RANK_FAULT_WHO_WRITE, RANK_FAULT_WHO_COMMIT,
    RANK_FAULT_WHO_RENAME, RANK_FAULT_WHO_STRAND,
    RANK_FAULT_SCR_WRITE, RANK_FAULT_SCR_COMMIT,
    RANK_FAULT_SCR_RENAME, RANK_FAULT_SCR_STRAND,
    RANK_FAULT_TXT_WRITE, RANK_FAULT_TXT_COMMIT,
    RANK_FAULT_TXT_RENAME, RANK_FAULT_TXT_STRAND,
    RANK_FAULT_RETIRE_RENAME            /* 移行時の NX93.TXT -> NX93OLD.TXT */
} RankFault;
```

`*_RENAME` と `*_STRAND` を分けるのは必須で、まとめると**仕様で定めた E14 が観測不能に
なる**。`*_RENAME` は差し替え rename だけを失敗させ、復帰 rename は本物を走らせる
（POSIX では成功するので **E14「rename 失敗・復帰成功」** が観測できる）。`*_STRAND` は
差し替えと復帰の両方を失敗させる（**E15 STRANDED**。POSIX では復帰 rename が必ず成功
するので、注入しない限り到達できない）。

まとめて「両方失敗」にすると、復帰が成功する経路を一度も通らなくなる。その経路は 3 段
コミットが存在する理由そのものなので、網を外せない。`*_COMMIT` は `rank_commit` に入る
前に戻るため代替にならない。

故障点は 16（4 枚 × 4 種）＋ `RETIRE_RENAME` ＝ **17**、＋ `NONE`。

## 4. 不変条件

- **I1 記録の消失順序**: どの経路でも、リセット前 `NX93.SCR` の既定行以外の各行は、
  容量規則（歴代 30 の床、ユーザ 100 人・1 人 1 件）が許す範囲で `RANK30.TXT` と
  `RANKWHO.TXT` のコミットに載った**後**でなければ `NX93.SCR` から消えない。
  コミット順 RANK30 → RANKWHO → SCR → TXT は厳密で、前段が失敗したら後段は走らない。
  反証: 故障注入で SCR が新しいのに RANK30 か RANKWHO が古い状態が観測されること。
- **I2 欠落の不在**: どの失敗でも 4 枚（＋`NX93OLD.TXT`）のどれも「欠落したまま黙って
  終わる」ことはない。唯一の例外は二重 rename 失敗（STRANDED）で、そのときは対象 1 枚が
  退避名の下に全バイト残り、メッセージが回復手順を名指す。
- **I3 併合の冪等**: 同じ候補列を `rank_merge30` / `rank_mergewho` に二度流しても、
  一度流した結果とテーブルがバイト同一。
- **I4 中断からの収束**: **STRANDED（E15）を除く**任意の 1 点で失敗した後、故障のない
  再実行は終了 0 で完了し、`RANK30.TXT` `RANKWHO.TXT` `NX93.SCR` は一発成功時とバイト
  同一、`NX93.TXT` はタイムスタンプ 19 バイトを除いて同一。
  `RANK30.TXT` `RANKWHO.TXT` `NX93.SCR` が STRANDED になった場合は、再実行だけでは
  収束しない。対象が不在なので再実行は 0 行から作り直し、退避名に残る旧バイトを読まない
  （`NX93.SCR` なら既定 10 行に戻る）。収束の経路は E15 のメッセージが示す手での rename
  のみである。`NX93.TXT` の STRANDED だけは、初回扱いの再リセットで収束する。
- **I5 無処理の無書き込み**: リセットが確定しない起動（終了 0 の無処理、および読み・検証
  段階での終了 1）は、どのファイルも作らず・消さず・1 バイトも書き換えない。
- **I6 既定行の不侵入**: プログラムが `RANK30.TXT` / `RANKWHO.TXT` に**追加する**行が
  出荷時 10 行のいずれかとバイト一致することはない（手置きされた既存行は温存・不増殖）。
- **I7 容量と形**: 成功後は常に `RANK30.TXT` ≤ 30 行、`RANKWHO.TXT` ≤ 100 行かつ
  key 相異、`NX93.SCR` ちょうど 10 行、`NX93.TXT` ちょうど 45 バイト。
- **I8 行の不加工**: 書き出される行はすべて、どこかから読んだ行（SCR・両表・旧台帳の
  デコード結果）か既定行のバイト列そのもの。
- **I9 一時物の衛生**: どの終了経路でも `RANKTMP.*` は残らない。`RANKOLD.*` が残るのは
  STRANDED の回復用コピーとしてだけ。`NX93OLD.TXT` は移行成功の正規の産物として残る。
- **I10 1 回だけ**: 境界を何本跨いでいてもリセットは 1 回、`lastUpdate` は実行時刻になる。
- **I11 実装制約**: ヒープ不使用、表は静的領域、ランキング行は printf 系書式引数に渡らない、
  `<ctype.h>` 不使用、ASCII のみ、C89 のみ、DOS 判定は `RANK_DOS` 一箇所
  （既存 S1〜S9 静的検査が引き続き全部緑であること）。
- **I12 再構築の冪等**: `rank_rebuild` の出力をもう一度 `rank_rebuild` に通すとバイト同一
  （§3.6 の埋め行除外によって成立する新しい性質）。

## 5. エラー分類

終了コードは全エラーで 1（`GAME.BAT` が PAUSE）。「残留」列が差し替わったものの全て。

| # | 条件 | 現行との対応 | 残留（何が書き換わったか） | 対処・再試行 |
| --- | --- | --- | --- | --- |
| E1 | 未知・過剰な引数 | 新規 | 無変更（何も開かない） | コマンド修正。再試行可 |
| E2 | ディレクトリ名が長すぎる | 既存 | 無変更 | 配置修正 |
| E3 | 時計が読めない | 既存 | 無変更 | 再試行可 |
| E4 | `NX93.TXT` の `lastUpdate` が取り出せない（破損） | 既存「台帳破損」 | 無変更 | 修復か削除（削除すると次回リセット） |
| E5 | `lastUpdate` が未来（秒粒度、同日内の巻き戻り含む） | 既存「未来日時」 | 無変更 | `DATE`/`TIME` で合わせる |
| E6 | `NX93.SCR` に読めない行・11 行以上・長すぎる行 | 既存 | 無変更 | 手で修復 |
| E7 | `RANK30.TXT` に読めない行・31 行以上・長すぎる行 | 新規（E6 の同型） | 無変更 | 手で修復 |
| E8 | `RANKWHO.TXT` に読めない行・101 行以上・key 重複 | 新規 | 無変更 | 手で修復。**文面は「`RANKWHO.TXT` を消せば次回に作り直される（過去の記録は `RANK30.TXT` に残る）」を含めること。**これを欠くと、鍵重複を手で書き込んだ利用者が毎起動 PAUSE から自力で抜け出せない（§3.8 の鍵変更で `OMZN` と `OMZN@@@@` が重複になるため、素人の手編集で実際に起こりうる） |
| E9 | 4 枚のいずれかが読み取り専用 | 既存（2 枚→4 枚に拡張） | 無変更 | `ATTRIB -R` |
| E10 | リセット確定時、`NX93.TXT` が正準形でなく `"backups"` も無い | 新規（誤破棄防止） | 無変更 | 手製なら削除、台帳の残骸なら退避・修復 |
| E11 | 移行発火時に `NX93OLD.TXT` が既にある | 新規 | 無変更 | `NX93OLD.TXT` を改名・移動 |
| E12 | 旧台帳が文法違反・不正エスケープ・読めない行・途切れ | 既存「backups 不能」の後継 | 無変更（取り込みはメモリ内） | 修復。直後の再実行で移行再試行 |
| E13 | 一時ファイル作成・書き込み・close 失敗（4 枚のどれか） | 既存「一時ファイル」 | 失敗した段より**前**のファイルだけ新しい。一時物は削除済み | 再実行で続きから収束（I4） |
| E14 | commit FAILED（差し替え rename 失敗、復帰 rename 成功） | 既存「差し替え失敗」 | 同上（対象ファイルは旧内容のまま無傷） | 再実行で収束。観測は `*_RENAME` 注入でのみ可能 |
| E15 | commit STRANDED（復帰 rename まで失敗） | 既存 stranded | 対象 1 枚が消え、旧バイトは退避名（`RANKOLD.30`/`RANKOLD.WHO`/`RANKOLD.SCR`/`RANKOLD.TXT`/`NX93OLD.TXT`）に残る。前段は新しい | メッセージの手順で rename して戻す。`NX93.TXT` の場合は再実行だけでも収束（初回扱いで再リセット、I4） |
| E16 | 移行の退避 rename 失敗（`RANK_FAULT_RETIRE_RENAME`） | 新規 | RANK30/WHO/SCR は新しい。`NX93.TXT` は旧台帳のまま無傷 | 再実行で移行をやり直し（冪等） |

警告（エラーではない）:

| # | 条件 | 終了 | 残留 |
| --- | --- | --- | --- |
| W1 | ユーザ 100 人超過で最下位を落とした | 0 | リセットは完遂。落ちた行は画面報告のみに残る（RANK30 に居れば歴代には残る） |
| W2 | 退避名に残っていた旧バイトを片付けた | 0 | リセットは完遂。退避コピーは消える |

**W2 の由来（2026-10-21 ユーザー決定）。** E15（STRANDED）の後、退避名は旧バイトを保って
残り、直後の再実行でも消えない（対象が不在なので `rank_commit` が削除経路を通らない）。
しかし**その次のリセットでは対象が実在するため、`rank_commit` 冒頭の「残骸 remove」が
唯一の回復コピーを消す**。`GAME.BAT` が毎日 `RANK` を呼ぶ運用では、2 回目の跨ぎ
（約 1 日後）に利用者が気づく前に消える。消す前に 1 行出す。終了コードは 0 のまま
（W1 と同じ精神。E15 自体が注入しない限り POSIX では起きないほど稀で、消える中身も
新しいファイル側にほぼ入っているので、運用を止めるほどの扱いにはしない）。

移行で作る `NX93OLD.TXT` はこの経路では消えない。通常実行の TXT 段の keep は
`RANKOLD.TXT` で、`NX93OLD.TXT` は二度と触られないため。

**メッセージは ASCII で書く。** 日本語は `GAME.BAT` の `ECHO` にしか置けない（§2 の
Shift-JIS 制約）。

## 6. 資源・並行性モデル

- DOS はシングルタスク、`GAME.BAT` は RANK → NX93 の逐次実行、テストハーネスは
  単一スレッド。ロックは置かない（現行どおり）。
- **読みと書きの分離**: すべての読み取り（SCR・両表・状態／旧台帳のスキャン・取り込み）を
  終え、全ハンドルを閉じてから最初の書き込みを行う。開いたままのファイルを rename しない。
- **有界性**: 書くファイルはすべて固定上限（45 B / ≤30 行 / ≤100 行 / 10 行）。
  唯一の非有界入力は旧台帳で、1 行バッファ（64 B）だけでストリーム処理する。
  丸読み・ヒープ確保はしない（既存 S4 検査が拘束）。
- **解放**: すべての `FILE*` は成功・失敗の全経路で close。一時ファイルは失敗経路で
  remove（I9）。中断時の残留状態は §5 の表が全列挙。
- **静的領域の見積もり**（DOS small モデル、`sizeof(RankRow)` = 86 バイト）:

| オブジェクト | 概算 |
| --- | --- |
| `RankWhoTable` ×1（101 行） | 8,688 B |
| `Rank30Table` ×1（31 行） | 2,668 B |
| `RankTable` cur/next（rank_run、既存） | 3,444 B |
| `RankTable` work（rank_rebuild、既存） | 1,722 B |
| パス緩衝 13 本 × 128（既存 6＋新 7: RANK30/WHO の本名・一時・退避、NX93OLD） | 1,664 B |
| 既定行・メッセージ等リテラル、行バッファほか | ≈ 3,200 B |
| **合計** | **≈ 21.4 KB** |

  受け入れ上限はクロスビルドの `.data + .bss` ≤ **32 KiB**（build.sh が表明する）。
  small モデルの 64 KB DGROUP にスタック約 2 KB とランタイムを足しても余白が残る。
  表・`RankRow` の大きな一時を自動変数に置かないこと（I11）。

## 7. 受け入れ基準

各基準は「入力 → 観測」。ファイルの比較はバイト比較、時刻は `RANK_TEST_CLOCK` で注入。

**A. 引数（E1）**
1. 無指定／`/W`／`/w` → 週次の判定が走る（下記 B 系で区別可能）。`/D`／`/d` → 毎日。
2. `/X`・`FOO`・`-D`・`/DD`・空文字列・引数 2 個（`/D /W`）→ 終了 1、
   stdout に `/D` と `/W` を含む usage、全ファイルバイト同一、`RANKTMP.*` 残存なし。
3. `rank_run(dir, 2)` など不正 mode → 1、無変更。

**B. 跨ぎ判定（§3.5。終了コードと 4 枚の変化有無で観測）**

| last | now | `/D` | `/W` |
| --- | --- | --- | --- |
| 2026-10-18T23:59:59 | 2026-10-19T00:00:00 | リセット | リセット（月曜 00:00 ちょうど） |
| 2026-10-18T23:59:59 | 2026-10-19T00:01:00 | リセット | リセット（日 23:59→月 00:01） |
| 2026-10-19T00:00:00 | 2026-10-19T23:59:59 | 無処理 0 | 無処理 0 |
| 2026-10-19T00:00:00 | 2026-10-25T23:59:59 | リセット | **無処理**（6d23h59m59s、同週） |
| 2026-10-19T03:00:00 | 2026-10-26T02:00:00 | リセット | **リセット**（6d23h でも月曜跨ぎ。旧経過規則との判別器） |
| 2026-10-20T23:59:59 | 2026-10-21T00:01:00 | リセット（同日 23:59→翌 00:01） | 無処理（火→水） |
| 2026-12-31T23:59:59 | 2027-01-01T00:00:00 | リセット（年越し） | **無処理**（木→金、月曜なし） |
| 2026-12-31T12:00:00 | 2027-01-04T00:00:00 | リセット | リセット（年越し後の月曜） |
| 2028-02-28T23:59:59 | 2028-02-29T00:00:00 | リセット（うるう日） | 無処理（月→火、同週） |
| 2028-02-29T23:59:59 | 2028-03-01T00:00:00 | リセット | 無処理 |
| 2028-02-28T12:00:00 | 2028-03-06T00:00:00 | リセット | リセット |
| last == now | | 無処理 0 | 無処理 0 |
| 2026-10-20T12:00:00 | 同日 11:59:59 | E5・1・無変更 | E5（同日内巻き戻り） |
| 2026-10-20T12:00:00 | 前日／1 年前 | E5 | E5 |

4. `rank_week_index` が §3.5 アンカー表の全行に一致。`rank_days_from_civil` の既存
   U-T1 アンカーは不変。
5. 14 日 / 3 週間ぶりの起動 → リセットは 1 回、`lastUpdate` = now（I10）。
6. 無処理の起動を 5 回連続 → 全て終了 0、4 枚バイト同一、stdout にモード字句（I5）。
7. `/D` でリセットした翌日に `/W` → 同週なら無処理 0。次の月曜 `/W` → リセット
   （モード無記録・双方向切り替えの観測）。

**C. 併合と再構築（単体）**
1. `rank_merge30`: 全バイト一致の重複は 1 件。既定行 10 本を流しても count 0。
   31 件目で最下位が落ち、同点境界では後入れが落ちる。二度流して不変（I3）。
   出力は降順・同点挿入順。
2. `rank_mergewho`: 同 key はスコアが真に大きいときだけ差し替え（同点は既存保持、
   報告なし）。新 key 101 人目で最終行が `*dropped` に入り戻り値 1。
   `OMZN`/`omzn`/`OMZN@@@@`/`omzn++++` は同一人、`TARO2` と `TARO` は別人、
   `omzn-2` は `omzn` と別人（§3.8 の鍵規則）。二度流して不変。
3. `rank_who_load`: key 重複ファイル → -1。101 行 → -1。`rank_r30_load`: 31 行 → -1。
4. `rank_is_default_line`: 出荷時 10 行で添字 0..9、1 バイト違いで -1。
5. `rank_rebuild`: 実機の現 `NX93.SCR`（実記録 6 行＋埋め 4 行）を入力したとき、出力は
   `327400 OMZN` 1 行＋出荷時 200000..040000 の 9 行で、200000 は**1 行だけ**、
   出荷時 020000 は押し出される。`OMZN@@@@`（299370）は §3.8 の鍵規則で `OMZN` に
   併合されるので現れない。出力をもう一度通してバイト同一（I12）。
   既存 U-M1〜U-M10 は新規則の期待値へ更新。
6. 鍵の正規化（§3.8 の表の全行を `rank_parse_line` 経由の `RankRow.key` で観測）:
   `omzn`/`OMZN`/`OMZN@@@@`/`omzn++++` → `OMZN`、`omzn-2` → `OMZN-2`、
   `TARO2` → `TARO2`、`Bio_100%` → `BIO_100`、`@@@@` → `@@@@`（規則 3 の退避）、
   空白 8 個 → 空。**「英数字の後に 0x80 以上のバイトが続く名前」（例: `omzn` ＋
   Shift-JIS 2 バイト、および `omzn` ＋ Shift-JIS ＋ `@`）が 1 バイトも落ちない**こと。
   この形に限定するのが必須で、「末尾が 0x80 以上の名前」と書くと表明が空振りする:
   全体が Shift-JIS の名前は、規則 2 で全部落ちても規則 3 の退避で元へ戻るため、
   「0x80 以上も落とす」誤実装でも正しい鍵が出てしまう。英数字が前にある形だけが
   退避に救われず、誤実装と正実装を区別できる。
   混在ケース: `@@@@omzn` は末尾が英数字なので何も落ちず `@@@@OMZN`、`OMZN` とは別人。

**D. リセット一式（`rank_run`、使い捨てディレクトリ）**
1. 新形式 `NX93.TXT`（45 B）＋境界跨ぎ → 終了 0。`RANK30.TXT` に SCR の非既定行が
   降順で入り、`RANKWHO.TXT` は 1 人 1 行、`NX93.SCR` は `rank_rebuild` の期待、
   `NX93.TXT` は now の正準 45 B。既定行は両表に現れない（I6）。
2. 同条件で再度境界を跨いで実行 → 4 枚すべて、`NX93.TXT` のタイムスタンプを除いて
   前回と同一（冪等の統合観測。I3 と I12 の合わせ技）。
3. `NX93.TXT` 不在（初回）→ リセット。`NX93.SCR` 不在 → 既定 10 行を書き、両表は
   空のまま（0 バイトのファイル）で終了 0。
4. 既存 `RANKWHO.TXT` 100 行＋新規 key を含む SCR → 終了 0、100 行のまま、落ちた行の
   raw バイトが stdout に現れる（W1）。落ちた行は表に無い。
5. 読み取り専用を 4 枚それぞれに付けた 4 変種 → 終了 1、全ファイル無変更（E9）。
6. 破損系: E4・E6・E7・E8・E10 の各入力 → 終了 1、全ファイルバイト同一、
   `RANKTMP.*` 残存なし。
7. 正準形から 1 バイトずらした `NX93.TXT`（LF 化・末尾余分・空白追加）＋跨ぎ →
   E10 で拒否（正準判定の完全一致性）。跨ぎが無い起動では同じファイルでも無処理 0。

**E. 移行**
1. 実機形状の旧台帳（`lastUpdate` 2026-10-08、backups 1 件 10 行）＋埋め行を含む現 SCR
   ＋跨ぎ → 終了 0。`RANK30.TXT` = SCR 非既定行 ∪ 台帳全行の行一致重複除去で降順。
   `RANKWHO.TXT` は key ごとの最高。§3.8 の鍵規則では SCR の `OMZN` `omzn` と
   `OMZN@@@@`、台帳の `omzn` 系がすべて同一人物 `OMZN` なので、**1 行（327400）だけ**に
   なる。`NX93OLD.TXT` が元 `NX93.TXT` とバイト同一。新 `NX93.TXT` は正準 45 B。
   stdout に退避の事実。
2. 同じ旧台帳で跨ぎ無し → 終了 0、**全ファイル無変更**（移行は繰り延べ）。
3. 移行成功の翌日 → 通常リセットのみ。`NX93OLD.TXT` バイト不変（二度目は走らない）。
4. 旧台帳 4000 件・2 MiB → 成功。ASan/UBSan 無反応（ストリーム処理）。
5. `ranking: []` の空配列を含む台帳 → 成功。
6. 破壊変種（`]` 欠落、`\x` 不正エスケープ、`\u0100`、26 バイトの行、64 バイト超文字列、
   文字列中の生 CR、`"ranking"` キー欠落、途中 EOF）→ それぞれ終了 1、全ファイル
   バイト同一（E12）。
7. `NX93OLD.TXT` を先に置く → 終了 1、無変更（E11）。
8. エスケープ復号: `\"` `\\` `\u005c` `\u0022` 入りの行が元のバイト列に戻って表へ入る。
   0x80 以上の生バイトは素通し。

**F. 中断耐性（故障注入 17 点）**
1. 各 `RANK_FAULT_*` について: 終了 1、注入点より前のファイルだけ新内容・以降は旧内容
   （I1 の順序）、`RANKTMP.*` 残存なし、メッセージが替わった／替わらないを正しく区別。
2. それぞれの直後に故障なしで再実行 → 終了 0 で収束し、RANK30/WHO/SCR はクリーン一発
   実行とバイト同一、TXT はタイムスタンプ以外同一（I4）。特に `TXT_*` 失敗後の再実行で
   RANK30/WHO/SCR に差分が出ないこと（冪等の実地観測）。
3. `RETIRE_RENAME` 注入 → RANK30/WHO/SCR 新・`NX93.TXT` 旧台帳のまま → 再実行で
   移行が完遂し E1 と同じ最終状態。
4. 事前に `RANKTMP.30` `RANKOLD.WHO` 等の残骸を置いても成功し、終了時に消えている（I9）。

**G. 静的検査・資源**
1. 既存 S1〜S9（ASCII のみ、C89、ヒープなし、テスト記号なし、ctype なし、書式注入なし、
   `RANK_DOS` 一箇所）が新ソースでも全部緑。
2. クロスビルドの `.data + .bss` ≤ 32 KiB（build.sh が表明）。
3. `mise run build:nx93rank` が MZ を出し、QuickC 想定の C89 制約（S2 相当）を破らない。

**H. 実機でのみ確認（Mac では範囲外、現行 tests/README.md と同じ扱い）**
`GAME.BAT` のスイッチ渡しと `errorlevel` 分岐、DOS の rename/remove 挙動、
`TYPE RANK30.TXT` の可読表示、NX93.EXE が新 SCR を読めること。

## 8. 記録すべき棄却案（architect の ADR 向け）

- **移行を検出即時に行う案** → 棄却。「リセットしない起動では何も書かない」（決定 3）と
  両立しないため、最初の跨ぎまで繰り延べる。
- **正準判定を緩くする（lastUpdate が読めれば新形式扱い）案** → 棄却。`"backups"` キーが
  潰れた旧台帳を「状態ファイル」と誤認し、記録ごと捨てる経路が開くため完全一致にした（E10）。
- **既存 `NX93OLD.TXT` の黙った上書き** → 棄却。「退避して消さない」の精神に反する（E11）。
- **上限超過を終了コード 2 にして GAME.BAT で PAUSE** → 棄却（2026-10-20 ユーザー決定）。
  終了コードの語彙を {0,1} に保つ。`errorlevel` は以上比較なので、分岐順を誤ると
  エラーと混じる危険もある。
- **落とした行を `RANKOUT.TXT` へ追記する案** → 棄却。無境界に伸びるファイルをやめる
  という今回の趣旨と衝突する。
- **RANKWHO を落とす際に新参を優先して残す案** → 棄却。同点は既存勝ち・最下位落ちのほうが
  冪等性と決定性の証明が単純。
- **`rank_rebuild` の埋め行重複を別件にする案** → 棄却（2026-10-20 ユーザー決定）。
  同じファイルを書き換える最中であり、規則 1 つの追加で消え、しかも冪等性（I12）という
  証明しやすい性質が手に入る。
