## 1. レベル配分の方針

| レベル | 何を置くか | 理由 |
| --- | --- | --- |
| 静的 (S) | DOS でしか壊れないもの（8.3、死にコード、自動変数の表） | Mac 上で実行しても絶対に現れない欠陥。grep と `nm` が唯一の網 |
| 単体 (U-A/U-C/U-K/U-F/U-G/U-V) | 引数・跨ぎ・鍵・行表 I/O・併合・旧台帳デコード | 純関数か `FILE*` 1 本。組み合わせ爆発はここで畳む |
| 統合 (I/X) | `rank_run` の順序・残留状態・冪等・移行・故障注入 | 「どのファイルが実際に替わったか」は `rank_run` でしか観測できない |
| 入口 (A) | `main` の argc/argv/終了コード/usage | `rank_mode_parse` の単体では argc の数え間違いも usage も捕まらない |
| 実機 (§7 H) | GAME.BAT・DOS の rename・TYPE・NX93.EXE・16 ビット `int` | Mac に DOS のバッチ意味論と 16 ビット `int` が無い |

跨ぎ判定と鍵規則は**単体に寄せる**（`U-C5` と `U-K1` の決定表が本体）。統合側は
「`rank_run` が本当にその規則を通っているか」の配線確認に留める。同じ論理を
遅い層で二度払わない。

## 2. 既存ケースの処遇

決定 7（既定行除外）と決定 8（鍵規則）は**別々に効く**。混ぜると、実装に合わせて
期待値を書き換える事故が起きるので分けて書く。

### 2.1 決定 7 では 1 件も動かない（重要）

**`U-M1`〜`U-M10` のどの入力も、出荷時 10 行とバイト一致する行を `cur` に持たない**
（`fix_scr`・`fix_bak` は全行 OMZN 系、`U-M5` の同点行は `AAA`/`BBB`、`U-M6` は空表、
`U-M7` は `AAA`/`BBB`/`CCC`、`U-M8` は `N0`..`N9`）。確認済み。

したがって**決定 7 単独では U-M* の期待値は 1 つも変わらない**。実装中に U-M* が
決定 7 のせいで赤くなったら、それは期待値の更新ではなく**回帰**。
決定 7 の網は新設 `U-G1`（既定行判定）と `U-G8`（実機 SCR）が張る。

## 6. 単体: プレイヤの同一判定 (U-K) — 決定 8 の核心

`rank_fold_key` は `static` なので、観測はすべて **`rank_parse_line` 経由の
`RankRow.key`**（§3.9）。既存 `U-P6` と同じ観測経路で、既存の `SCORES` 4 桁数
（1/5/6/9 桁）すべてで回す（名前欄の切り出し位置が桁数で動く事故を踏むため）。

### 6.1 **警告: 「0x80 以上で止める」を殺せる入力は 2 形だけ**

この規則は仕様が「必須条件であって最適化ではない」と明記している最重要点だが、
**素朴に用意した Shift-JIS 名では網にならない**。17 名前 × 5 変異で全数評価した結果:

| 名前の形 | `stop_high` を外した実装 | 理由 |
| --- | --- | --- |
| `\x82\xa0\x82\xa2`（全バイト ≥0x80） | **検出できない** | 全部落ちて空になり、**規則 3 の退避が元に戻してしまう**ので正解と一致する |
| `\340abc\300def`（末尾が英数字 `f`） | **検出できない** | 末尾が英数字なのでどちらの実装でも 1 バイトも落ちない |
| **`omzn\x82\xa0`（英数字の後に ≥0x80 が末尾）** | **検出できる** | 誤実装は末尾 2 バイトを落として `OMZN` を出す。正解は `OMZN\x82\xa0`。空にならないので規則 3 は助けない |
| **`omzn\x82\xa0@`（≥0x80 の後に ASCII マーク）** | **検出できる** | 正解は `@` を落として `OMZN\x82\xa0` で止まる。誤実装は `OMZN` まで落ちる |

したがって `U-K3` は**この 2 形を必須**とする。既存 `U-P6` の 2 つの高位バイト行
（`\340abc\300def`・`\340\300…`）は**この欠陥を通してしまう**ので、それを残すだけでは
不足である。仕様 §7 C.6 の字面「末尾が 0x80 以上のバイトの名前は 1 バイトも落ちない」も、
全 Shift-JIS 名で満たせてしまうので表明としては弱かった。**N1 として差し戻し、
2026-10-22 に仕様 §7 C.6 が「英数字の後に 0x80 以上のバイトが続く名前」へ改訂された。**
`U-K3` はこの新字面に対応している。

**同じ 2 形が「符号付き `char` で比較した」実装も殺す。** `char` が signed な処理系では
`c >= 0x80` が常に偽になり、0x80 以上のバイトが「英数字でない」と判定されて落ちる。
この 2 つの誤り（規則を書き忘れた／`unsigned char` を忘れた）は**観測上まったく
区別できない**ので、1 ケースが両方を殺す。それでよい（区別する価値がない）。

## 9. 単体: 旧台帳の取り込み (U-V)

### 9.1 移行フィクスチャの扱い

**決定: 実機 `hdd/game/nx93/nx93.txt` を原本とし、LF 版と CRLF 復元版の 2 本を
`fixtures_daily.h` に生成物として埋め込む。合成は追加分だけに使う。**

- 計測した: 581 B・**LF 20 本・CR 0 本・非 ASCII 0 バイト**。つまり `98hdd pull` の
  Shift-JIS→UTF-8 の脚は**この 1 本については恒等変換**で、実機バイト列との差は
  **改行だけ**。将来の pull で日本語が入れば崩れるので、再生成手順に
  「非 ASCII 0 バイトの再確認」を含める。
- `fix_ledger_lf`（581 B）= pull の写し、バイト厳密。
- `fix_ledger_crlf`（**601 B** = 581 + LF 20 本）= 全 LF を CRLF に書き換えた**復元**。
  逆変換（CR 全削除）で `fix_ledger_lf` に戻ることを生成時に確認する（確認済み）。
- §3.4 の `ws := (SP|TAB|CR|LF)*` が CRLF と LF の差を文法として吸収するので、
  この 2 本は**同じ結果を出さなければならない**。メタモルフィック関係として表明（`U-V3`）。
- **限界の明示**: `fix_ledger_crlf` は実機を**観測したものではなく再構成**。
  「98 上の `NX93.TXT` が本当にこのバイト列か」は §7 H（実機確認）の範囲。
  設計はそれを前提にせず、「両改行で同結果」という**より弱く正しい**表明に落としている
  （F10 の回答どおり維持）。
- `hdd/` はテストから読まない（実機ミラー）。再生成は手作業・`cmp` 確認つき。

**合成で足すもの**（実機 1 本では張れない網）: 文法破壊 18 変種・エスケープ入り・
2 MiB・空配列・鍵衝突・容量超過・同点。実機台帳は backups 1 件・エスケープ 0 個・
同点 0 組・14 行なので、文法も容量も同点規則も触れない。

### 9.3 `U-V4` の 18 変種

`"backups"`（**9 バイト**）のバイト列を全変種に含める。含めないと移行が発火せず
E10 になり、別の欠陥を試していることになる。

| 破る規則（§3.4） | 変種 |
| --- | --- |
| `'"backups"' ws ':'` | `"backups" [ ... ]`（`:` 欠落） |
| `ws '['` | `"backups": null` / `"backups": {}` |
| `']'` | 末尾の `]` 欠落（途中 EOF） |
| `'}'`（外側） | `]` の後で EOF |
| `ws 0x1A? EOF` | `}` の後ろに `garbage` |
| `entries` のカンマ | `[{…},]`（末尾カンマ）/ `[{…}{…}]`（カンマ欠落） |
| `entry` の `'{'` | `["backupAt": …]` |
| `'"backupAt"'`（10 B） | キー名を `"when"` に |
| `'"ranking"'`（9 B） | **`"ranking"` キー欠落**（§7 E.6 指定） |
| キーの順序 | `"ranking"` を `"backupAt"` の前に |
| `entry` の `'}'` | エントリの閉じ `}` 欠落 |
| `strings` のカンマ | `["a" "b"]` |
| `string` の閉じ `"` | 閉じ引用符なしで EOF |
| `char`（生制御文字） | 文字列中に**生 CR**（§7 E.6 指定）/ 生 LF |
| エスケープ | `\x41` / `\u00` ＋ `G0`（非 hex）/ `\u` ＋ `0100`（4 桁が 00XX でない。§7 E.6 指定） |
| 行の長さ | デコード結果が **26 バイト**の行（指定）/ **36 バイト**の行 |
| 行のパース | スコアに非数字 / 区切り位置が空白でない |
| 文字列の長さ | デコード後 **64 バイト超**（指定） |

**prefix の誤マッチ（設計で足す 1 件）**: 先頭側の別の文字列値の中に
`\"backups\": [` を仕込んだ台帳。§3.4 の論証は名前欄 8 バイトを対象にしているが
（9 バイトの `"backups"` は 8 バイトの名前欄に収まらない）、`rank_has_backups` は
生バイト走査なので手編集ファイルでは起こりうる。オラクルは**全か無か**:
「−1 で表が無変更」か「0 で表が一貫」のどちらかであり、中途半端な取り込みに
ならないこと。正しい実装はどちらでも通る。

### 9.4 エスケープの復号表と拒否表（`U-V1` / `U-V2` のオラクル）

**表記について**: `\u` に続く 4 桁を書くと処理系によって文字そのものへ変換されて
しまうため、この節では**接頭辞と hex 部を分けて**書く。
`` `\u00` ＋ `22` `` は 6 バイトのバイト列 `"` を意味する。

**復号表（`U-V1`。すべて成功し、右の 1 バイトになる）**

| 入力のバイト列 | デコード結果 | 狙い |
| --- | --- | --- |
| `\"` | 0x22 | 二文字エスケープ |
| `\\` | 0x5C | 二文字エスケープ。**SJIS 名の第 2 バイト問題の本体** |
| `\u00` ＋ `22` | 0x22 | 数値形でも同じ結果 |
| `\u00` ＋ `5c` | 0x5C | **hex 小文字** |
| `\u00` ＋ `5C` | 0x5C | **hex 大文字**（§3.4「大小とも可」） |
| `\u00` ＋ `00` | 0x00 | 下端。旧 writer が制御文字を逃がした形 |
| `\u00` ＋ `1f` | 0x1F | 制御文字の上端 |
| `\u00` ＋ `ff` | 0xFF | 上端。0x80 以上も数値形で書ける |
| 生の 0x80..0xFF | そのまま | 素通し（§3.4）。SJIS 名が無傷で戻ること |

長さ境界: デコード後 **63 B → 成功・戻り値 63**／**64 B → −1**。空文字列 `""` → 0。

**拒否表（`U-V2`。すべて −1）**

| 入力のバイト列 | なぜ不受理か |
| --- | --- |
| `\x41` | §3.4 の `char` に無い |
| `\n` / `\t` / `\/` / `\b` | **§3.4 は二文字エスケープを `\"` と `\\` だけに限る**。旧 writer は制御文字を数値形へ逃がすのでこれらを出さない |
| `\u` ＋ `0100` | 00XX 以外（§7 E.6 指定） |
| `\u` ＋ `D800` | 同（非対サロゲート） |
| `\u00` ＋ `G0` | hex でない |
| `\u00` で EOF | 桁が足りない |
| `\` で EOF | エスケープが切れている |
| 閉じ `"` なしで EOF | 文字列が終わらない |
| 文字列中の生 0x0D | **§7 E.6 指定**（生 CR） |
| 文字列中の生 0x0A / 0x09 / 0x00 | 生の 0x00–0x1F は不受理（§3.4） |
| 文字列中の生 **0x1A** | 同。加えて 0x1A を EOF と誤読する実装も落ちる |

### 10.6 故障種別ごとの残留状態（`I-43` のオラクル表）

注入した段の対象ファイルを「対象」、それより前の段を「先行」、後の段を「後続」と書く。
どの行でも終了コードは 1、`RANKTMP.*` は残らない、先行は新内容、後続は旧内容。

| 故障種別 | §5 | 対象ファイル | 対応する退避名 | 回復 |
| --- | --- | --- | --- | --- |
| `*_WRITE` | E13 | **旧内容のまま実在** | 生まれない | 再実行で収束 |
| `*_COMMIT` | E13/E14 | **旧内容のまま実在** | 生まれない（`rank_commit` に入る前に戻る） | 再実行で収束 |
| **`*_RENAME`** | **E14** | **旧内容のまま実在**（復帰 rename が成功した証拠） | **消えている**（復帰で使い切る） | 再実行で収束 |
| **`*_STRAND`** | **E15** | **消失** | **旧バイトが全バイト残る** | 手で rename、または再実行（`NX93.TXT` は初回扱いで自動収束） |
| `RETIRE_RENAME` | E16 | `NX93.TXT` が旧台帳のまま無傷 | — | 再実行で移行をやり直し |

`*_COMMIT` と `*_RENAME` は**対象ファイルの状態が同じ**（旧内容のまま実在）。
区別は「退避名を経由したか」であり、Mac 上では**両者を残留バイトで区別できない**。
そこで `*_RENAME` の表明には **stdout の差分**（`A-6` と同じ要領で `*_COMMIT` の文面と
byte-equal でないこと）を足す。これが E14 を E13 から分ける唯一の観測面である。

### 10.7 W2（退避の片付けの予告）— `I-53` のオラクル

N6 の決定（2026-10-21）: 退避名の旧バイトを片付ける**前に画面 1 行出す。終了コードは 0 のまま**。

**3 段の列**（1 変種 = 1 ファイル。基線は 4 枚実在）:

| 段 | 操作 | 終了 | 退避名 | **W2** |
| --- | --- | --- | --- | --- |
| 1 | `<X>_STRAND` を注入 | 1 | **旧バイトを保って出現** | **出ない**（まだ片付けていない） |
| 2 | 故障なしで再実行（次の跨ぎ） | 0 | **元バイトのまま残る** | **出ない**（対象が不在で削除経路を通らない） |
| 3 | もう一度跨いで実行 | **0** | **消える** | **出る** |

**機械オラクル**（§3.2 が「字面は実装の裁量」としているので、要素ごとに強さを分けて書く）:

1. **退避名**（`RANKOLD.30` / `RANKOLD.WHO` / `RANKOLD.SCR` / `RANKOLD.TXT`）が
   stdout に**完全一致の部分文字列として現れる**。— 完全に機械的。
2. 「消える」— **語彙集合のいずれかが現れる**: `discard` / `discarded` / `delete` /
   `deleted` / `remove` / `removed` / `removing`。
3. 「必要なら次回起動前に退避せよ」— **語彙集合のいずれかが現れる**: `save` / `rename` /
   `copy` / `keep` / `before`。
4. **W2 行は ASCII のみ**（全バイト < 0x80）。`S1` はソースの ASCII 性を張るが、
   実行時出力の表明もここに置く（日本語は `GAME.BAT` の `ECHO` にしか置けない）。
5. 段 3 の**終了コードが 0**（W1 と同じく語彙を {0,1} に保つ。`A-3` が横断でも見る）。
6. 片付けた退避名**1 本につき 1 報**（§3.2）。4 本同時に片付く `I-46` ① では 4 報。

> **2 と 3 は語彙的な代理であって文意の検証ではない。** 文面が実際に読んで分かるか、
> 助言が有効かは §12.3 のとおり **audit の人手レビュー**に委ねる。語彙集合を設計側で
> 宣言しておくのは、「ファイル名だけ出して何をするか言わない」実装を落とすための
> 下限であり、字面を 1 通りに固定するものではない。

**W2 が出てはいけない負の変種（2 つ）**:

- **残骸が無いクリーンなリセット**（`I-26` と同じ入力）→ stdout に W2 の語彙が**現れない**。
  これが無いと「毎回 W2 を出す」実装が緑で通る。
- **無処理の起動**（`I-23`）→ commit に入らないので当然 W2 は出ない。

**4 枚すべてを採る（代表を採らない）理由**: 片付けは `rank_commit` の**単一の呼び出し元
共通コード**で起きるので、退避名は引数として渡ってくる。**ファイル名をハードコードした
実装は 1 変種だけ通って残り 3 つで落ちる**という、まさにこの defect class を狙うため、
代表化すると網が消える。1 変種あたり `rank_run` 3 回なので費用は小さい。

## 12. 何を試験しないか

### 12.1 実機でしか見られないもの（§7 H。Mac では原理的に不可）

- `GAME.BAT` のスイッチ渡しと `if errorlevel 1` の分岐順。DOS のバッチ意味論が無い。
- DOS の `rename`/`remove` の意味論（対象が在ると失敗する、読み取り専用は消せない）。
  POSIX は置き換えてしまうので、**`rename` の失敗を前提にした 3 段 commit の
  必要性そのものは Mac 上で観測できない**。`I-46` ②（名前をディレクトリで塞ぐ）が
  唯一の踏み台で、これは実機の欠陥を Mac で捕まえるための代用。
- `TYPE RANK30.TXT` が 98 の画面で読めること（この機能の目的そのもの）。
- `NX93.EXE` が新しい `NX93.SCR` を読めること。ブラックボックス。
- QuickC 2.00 / ia16 のコード生成、16 ビット `int`、small モデルのセグメント境界。
- **取り込み行数を `int` で数えた場合の溢れ**（2 MiB 台帳は 40000 行になり得る）。
  ホストの `int` は 32 ビットなので**どう書いても緑**になる。
  F8 の回答どおり architect へ「行数を数えない（併合は 1 行ずつ完結する）」を
  設計制約として渡した。数える必要が出たら `long` 必須＋`S11` と同型の grep 検査。
- 実機の `NX93.TXT` が本当に 601 バイト（CRLF）であること（F10。`fix_ledger_crlf` は
  復元であって観測ではない）。実機送信時にユーザーが実測して progress.md に記録する。
- `.data + .bss` の実測は docker 依存なので `verify` には繋がない（`G2` は build.sh 側）。

### 12.2 設計として意図的に落としたもの

- **移行 × 故障注入の 11 組**（§10.5 に理由と**復活条件**を明記）。
- **モード × 故障注入**、**モード × 移行**。モードは確定の有無しか決めない。
- **並行性・ロック**。DOS はシングルタスク、`GAME.BAT` は逐次。
  ただし `NX93OLD.TXT` の「存在検査 → 後で rename」は check-then-act であり、
  POSIX 上では競合しうる。DOS では無害なので**既知として落とす**。
- **タイムゾーン・夏時間・うるう秒の意味論**（§2 非目標）。TZ 3 本での不変性
  （既存 run.sh）だけを保ち、「どの TZ が正しいか」は問わない。
- **`Bio_100` という名前の実在プレイヤが既定行と同一人物になる経路**。決定 8 で
  既定行の鍵が `BIO_100%` → `BIO_100` に変わるが、**現行も同じ構造の衝突を持つ**ので
  決定 8 が作った問題ではない。既定行除外はバイト一致なので実害は
  「その人の記録が `RANKWHO.TXT` で既定行と 1 席を争う」に留まる。
- **`RANK30.TXT`/`RANKWHO.TXT` からの復元・剪定・編集**（§2 非目標）。
- **モードの永続化**（§2 非目標）。`NX93.TXT` に `mode` 欄が**無い**ことは
  `U-F5` のバイト一致が自動的に保証する。
- **`NX93.BAK`**。ゲーム本体の持ち物（§2）。テストは読みも書きもしない。
- **`rank_run` 内部の関数分割・引数の順序**。内部。
- **SJIS 2 バイト文字の第 2 バイトが a-z 畳み込みを巻き込む問題**。既存の「既知の限界」を
  引き継ぐ。決定 8 は末尾落としを 0x80 で止めるので**この問題を悪化させない**が、
  解消もしない（`U-K7` ②が「鍵に小文字が残らない」までを見る）。
- **カバレッジ率**。目標にしない。§14 のミューテーション表が網の証拠。

### 12.3 メッセージ検証の線引き（F7 の回答を明文化）

§3.2 は「文字列の字面は実装の裁量」と定めている。したがって機械オラクルは次の
**2 点だけ**とし、それ以外は **audit の人手レビュー項目**として残す。

| 機械で見る | どのケース |
| --- | --- |
| 実際にバイトが変わったファイルの基本名が文面に現れる | `I-43`・`I-45`・`I-51` |
| 11 のエラー条件の文面が互いに byte-equal でない | `A-6` |
| 有効なモードの字句・経過日数・`NX93OLD.TXT` の字句・W1 の raw 32 バイト・usage の `/D` `/W` | `A-1`・`A-5`・`I-30`・`I-31`・`I-37` |

**人手レビューに委ねる（試験しない）**: 対処が実際に有効か（`DATE` で直るのか、
`ATTRIB -R` が正しい助言か、退避名からの rename 手順が本当に回復するか）、
日本語話者にとって読めるか、`GAME.BAT` の PAUSE で流れずに読めるか。
これらは自然文の正しさなので機械オラクルを持たない。audit の項目として明示すること。

### 15.1 実装の入口で踏みやすい罠（`rank_commit` を読んで分かったもの）

T1/T2 から入る implementer 向けに、設計側で気づいた分を明示する。
どれも既存ケースが赤で捕まえるが、先に知っていれば一度で通る。

1. **`rank_commit` は故障フラグを 2 本必要とする。** 現行は `fail_rename` 1 本。
   `*_RENAME`（差し替えだけ失敗＝E14）と `*_STRAND`（復帰まで失敗＝E15）を
   分けるので、`fail_rename` と `fail_strand` の 2 引数（または 2 ビット）になる。
   1 本にまとめると **E14 が観測不能**になり `I-18`・`I-43` の `*_RENAME` 4 点が死ぬ。
2. **移行の TXT 段で `rank_commit` をそのまま使うと `NX93OLD.TXT` を消す。**
   成功経路の末尾に `if (saved) remove(keep);` があるため、keep を `NX93OLD.TXT` に
   しただけでは **成功と同時に退避が消え、§3.7 の「成功しても削除しない」に反する**。
   keep を残す変種（引数 1 本、または移行専用の commit）が必要。`I-37`・`I-39` が赤で捕まえる。
3. **W2 は「実際に消したとき」だけ出す。** 片付けは `rank_commit` 冒頭の
   `if (rank_exists(dst)) { remove(keep); ... }` で起きる。keep が無いのが通常なので、
   **`remove` の前に keep の存在を確かめてから報告する**こと。無条件に報告すると
   毎回 W2 が出て `I-53` の負の変種と `I-26` が赤くなる。
4. **W2 は退避名を知る必要がある。** 共通コードで起きるので、名前は引数で渡ってくる
   ものをそのまま出す（ハードコードすると `I-53` の 4 変種のうち 3 つが赤）。
   ランキング行ではないのでファイル名は `printf` 書式に渡してもよいが、
   `S7` の検査は書式引数が文字列リテラルでないことを拒むので `fputs` 系で出すのが安全。
5. **`*_STRAND` は対象が実在しないと E15 にならない**（§10.5 の基線の節）。
   実装側の含意として、**`!saved` の「失うものが無い」経路を消してはいけない**
   （消すと対象不在時に STRANDED を返して `I-52` が赤くなる）。
6. **`expect_no_temps` は 13 本を見るが、`*_STRAND` では退避名 1 本が残るのが正しい。**
   ヘルパを「残ってよい退避名を 1 本受け取る」形にしてから故障ケースを書くこと
   （先に書くと全 `*_STRAND` ケースが偽の赤を出して原因を探す時間が無駄になる）。

**`mise.toml` へのスニペット案（実装が緑になってからユーザーが足す）**:

```toml
[tasks."verify:nx93rank-daily"]
description = "NX93 毎日更新の回帰テスト"
run = "nx93rank/tests/run-daily.sh"
```

あわせて `verify:syntax` の対象リストに `nx93rank/tests/run-daily.sh` を足す
（`bash -n` の対象）。`verify:encoding` の対象にも足す。
